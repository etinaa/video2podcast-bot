## A: Q-analyst-1 · architect
Contract is in `tasks/T16/api.md` (and flows.md, components.md). Summary:
- Endpoints: Whisper `GET <base>/`, Ollama `GET <base>/api/version`. I did not use `/health`: not every whisper.cpp build has it.
- Success = reachability: ANY HTTP status code received (including 404/503) counts as reachable; body ignored. Not 2xx only. The check answers "can we connect and does an HTTP server answer", which is what the two existing messages say ("unreachable"). Model readiness (503 while loading, missing Ollama model) is out of scope; those cases stay with the T9/T10 mid-job failure paths. Please word scenarios as "no connection / no answer in time", not "not ready".
- Budget: `app.health.timeout` (env `HEALTH_TIMEOUT`, default PT3S) per probe, separate from the 10-minute inference timeouts. Both probes always run, in parallel. Aggregate upper bound: timeout + 1 s grace = 4 s by default.
- Threading: preflight does NOT run on the Telegram polling thread (single-thread consumer) and not in `UrlMessageHandler.handle`. It runs first in `PipelineService.execute` on the job worker, so polling, other users' messages and taps are never blocked. It can occupy the single worker for at most 4 s per down job; this is accepted (it also means a job that waited in the queue is probed just before it starts).
- Observable order for the user: `Queued: position N`, then the failure message (both sentences in one message when both are down), then `Failed.` on the status message. No directory created, no yt-dlp call.
- Startup: log one line per service on a virtual thread after the context is ready; bot starts regardless.
- Coverage: no objection to your audit; pending-access full-context restart needs a new scenario.
