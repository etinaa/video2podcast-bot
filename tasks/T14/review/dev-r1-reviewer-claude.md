## Findings
- [Important] src/main/java/com/video2podcast/config/TelegramConfig.java:46 - `telegramBot` has no `@DependsOn("retentionSweeper")`; the patch does not touch `TelegramConfig`, and nothing in `src/main` or `src/test` mentions `DependsOn`. api.md ("Startup ordering contract") and components.md require it. `botUpdateHandler` and `telegramBot` do not depend on `retentionSweeper`, so Spring may create the bot, and the starter's `TelegramBotInitializer` may start long polling, before `recoverAtStartup()` has run. A tap could then race recovery: a SENDING file would be claimed or swept before it is reset, and unusable directories would be read. R1 ("Startup recovery must resolve ... before normal callbacks") is not enforced.
- [Important] src/test/java/com/video2podcast/config/ - the ordering tests that api.md assigns to the Developer are missing: an `ApplicationContextRunner` test asserting recover runs before the bot bean is created, and an assertion that the `telegramBot` bean definition has `retentionSweeper` in `getDependsOn()`. `JobConfigTest` only checks that recovery happened and that scheduling is enabled.
- [Important] src/test/java/com/video2podcast/job/JobStoreRetentionTest.java - no test of the claim vs. sweep lock interleaving. requirements.md R4 says "Deterministic lock interleavings are Developer unit-test obligations". Needed: (a) the sweep wins and a later `transition(AVAILABLE->SENDING)` returns NOT_FOUND/STATE_MISMATCH (no job, or the file is EXPIRED); (b) a claim wins and the sweep returns none() even after the deadline. Right now only the static "a SENDING file means none()" case is covered, not the exactly-one-wins contract.
- [Important] src/main/java/com/video2podcast/job/JobStore.java:201-214,366-381 - symlink safety (R6: "Following a symlink must never delete the link target outside WORK_DIR") is neither handled nor tested. `jobIds()` filters with `Files::isDirectory`, which follows links, so a symlink named like a job id pointing outside `WORK_DIR` is enumerated. `read` then reads the target's `job.json`. `recover` (no usable record) and `sweep` (finished) go to `deleteRecursively`: `Files.walk(link)` without FOLLOW_LINKS yields only the link, but `Files.deleteIfExists(dir.resolve("job.json"))` deletes the external file through the link. `sweep`'s `deleteFile(resolve(...))` also deletes inside the target. R6 explicitly puts these cases in unit tests, and none exists. Fix: use `Files.isDirectory(p, NOFOLLOW_LINKS)` in `jobIds()` (or skip `Files.isSymbolicLink`), and add a test with an external sentinel.
- [Suggestion] src/main/java/com/video2podcast/job/RetentionSweeper.java:371,387 - only `JobStoreException | IllegalArgumentException` are caught, while the class javadoc and api.md say "Never throws". A `RuntimeException` from `buttons.refresh` (the lambda fallback or a future implementation) would abort the whole pass and, at startup, the init method (and so the context). Catch `RuntimeException` per job (and when listing ids) so one bad job cannot stop the others (R8).
- [Suggestion] src/main/java/com/video2podcast/job/JobStore.java:266-273 - if deleting the 2nd file fails after the 1st was deleted, the 1st stays AVAILABLE on disk with the file gone. It is self-healing on the next pass (deleteIfExists), so no change needed, but a short comment would help, since the unit test for the failure only covers a directory permission case.
- [Suggestion] src/main/java/com/video2podcast/config/JobConfig.java:95 - the no-op `job -> {}` fallback is not covered for the "Telegram disabled" path beyond `worksWithoutTelegram`; that test is fine. No action required.
