## Requirements
- R1: met - `UrlMessageHandler` parks on `isServiceOutage()` (`SERVICE_UNREACHABLE` and `SUMMARY_UNREACHABLE`, including the combined case). Other kinds are untouched, and a failed park falls back to the normal failure message.
- R2: met - `DeferredJobs` writes through `AtomicFiles` behind `synchronized`, and the in-memory queue is swapped only after a successful write. The file holds only the minimal fields. It keeps order, handles a missing file, renames a corrupt or invalid file to `.corrupt-<epoch>`, and sits next to `ACCESS_FILE`. Parking order and attempt updates in place are tested.
- R3: met - a retry builds a new `JobRequest` with a fresh job id and runs the whole pipeline from scratch. Queue entries live outside the work directories, so retention and the sweep do not touch them. Retention of a successful retry starts at publication, as normal. Deleting the working directory after an outage is the existing pipeline behaviour, which the integration tests cover.
- R4: met - the parked case does only one `editStatus(PARKED)`. The retry passes `NO_PROGRESS`, so there are no later edits and the notifier sends nothing on an outage. A failed edit is logged and never touches the entry.
- R5: met - `@Scheduled` fixedDelay and initialDelay both read `app.deferred.retry-interval`. The defaults are `PT2H` and `12`, and validation rejects non-positive values. One pass walks a snapshot in FIFO order, runs each entry on the shared `JobQueue`, and `passRunning` stops overlapping passes. New entries wait for the next pass.
- R6: met - on success the entry is removed and the status is edited to `Done.`. The summary comes from the normal pipeline publisher, and nothing is uploaded automatically.
- R7: met - parking stores 0 attempts, and each outage on retry adds 1. `attempts >= maxAttempts` removes the entry and calls `gaveUp` once, which sends the fixed text and edits to `Failed.`. With maxAttempts 2 the first outage stays and the second closes. The tests cover the boundary. The count is persisted, so a restart does not reset it.
- R8: met - any other `JobFailure` or `RuntimeException` removes the entry and calls `failed`, which sends the escaped normal message and edits to `Failed.`. The next entry continues.
- R9: met - `hasAccess` is checked at the start of `retry`, on the worker, so it also covers entries that waited behind another job. Without access the entry is removed with no pipeline run, no Telegram call and one INFO log of the id. `AccessService.isAllowed` keeps the owner unconditional.
