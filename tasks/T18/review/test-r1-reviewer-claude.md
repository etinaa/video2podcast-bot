## Findings
- [Important] src/it/java/com/video2podcast/functional/DeferredSteps.java:589-610 (`singleChunk`, `singleDownload`, `singleSummary`) - The scenario "A tick during a held retry does not submit that entry twice" cannot detect the bug it targets. If the second tick submits the entry again, the duplicate waits behind the held worker. At that point the checks (one Whisper chunk, one download) still pass, because the duplicate has not started. After the release, `singleSummary` calls `summary()` and then immediately checks `w.summaries()).hasSize(1)`. That check runs as soon as the first summary arrives, before a duplicate run could produce a second one. `empty()` only waits for the first removal. Fix: after the release, wait until the entry is gone and the worker is idle (for example a short quiescence check, or wait for the status edit count to stop changing). Then assert one download, one Whisper chunk, one summary and one "Done." edit for the entry.
- [Important] src/it/java/com/video2podcast/functional/FailureModeWorld.java:191 with DeferredSteps.java:403-407 and 667-670 (`failures`, `noFailure`, `noFallback`) - Both "no separate service-failure sendMessage" and "no fallback outage sendMessage is attempted" use `failures()`, which only matches texts containing "server is unreachable.". R4 and the rejected-edit scenario forbid any fallback or duplicate message. A fallback `sendMessage` with the parked text, with `GAVE_UP`, or with a generic failure text would pass these steps. Fix: for the submission's chat, assert that no `sendMessage` is sent after the "Queued:" message. In the rejected-edit scenario, also assert that no `sendMessage` carries `PARKED` or `GAVE_UP`.
- [Suggestion] DeferredSteps.java:176-179 (`chatRequest`) - The step says "receives a POST request to /api/chat" but only checks the URL, not the method. Check the method too if `Event` has it.
- [Suggestion] DeferredSteps.java:472-477 (`firstText`) - This Given only checks that Whisper saw some request and that the configured body contains the text. It does not check that the first run returned that text. It is only setup, so it is acceptable. The "Fresh transcription" check in the Ollama request is what proves the retry started from scratch.
- [Suggestion] DeferredSteps.java:651 (`noRevokedWork`) - The `ollamaBefore + (whisperBefore > 0 ? 1 : 0)` expectation hard-codes the held-user-101 scenario inside a shared step. A separate step, or an assertion filtered by chat or request, would be clearer. It is correct for both scenarios today.
- [Suggestion] DeferredSteps.java:703-706 - `unchanged()` ("the original parked status has been left unchanged") is not used by any scenario in the feature. Delete it.
- [Suggestion] RetentionSetupSteps.java:85-90 and 220-226, RetentionAssertionSteps.java:176-181 - The T14 steps now branch on `pipeline.deferred` or `pipeline.active` to be reused by T18.
