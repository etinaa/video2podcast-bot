## Findings and design risks

1. **Counts require an explicit estimation policy.** The chat API defines a token count, not an exact tokenizer endpoint or a portable transcript-character conversion. An estimate can differ naturally from the actual count. The tolerance must distinguish ordinary estimation error from clear truncation, with threshold tests. A: Q-analyst-1 fixes an architecture threshold of half the estimated complete input; boundary tests cover the exact cutoff. This remains a heuristic and does not prove detection of every possible truncation.
2. **Budget the reduce phase too.** Context-safe transcript chunks do not imply that their summaries all fit one final prompt. The architecture must specify intermediate bounds/grouping and progress toward termination, preserving every partial. N map calls plus one reduce is only correct when the N partials fit together.
3. **Token output limits do not enforce character limits.** The final text must be capped deterministically, including markers/newlines and a defined Unicode policy. Prompting provides the language/style instruction; WireMock proves request/format/length behavior, not real semantic quality.
4. **Availability failures must remain actionable.** A bounded failure identifying the summary server is required. Do not inherit Whisper's retry count or its transcription-specific failure sentence without an explicit contract. Background recovery, deferred retry queues and cleanup are outside T10.
5. **An HTTP observation alone does not create an acceptance trigger.** T10 has no inbound HTTP endpoint or Telegram summary handler. Tests that directly call OllamaClient or SummaryService remain unit tests even when WireMock records outbound traffic. Gherkin waits for T11's real Telegram trigger; no internal service calls appear in the feature.

This is attributed peer evidence, not a new measurement performed by the Analyst; see [`api.md`](api.md) and [`comms/questions.md`](comms/questions.md).
