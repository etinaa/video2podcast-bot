## Findings
- [Important] src/it/java/com/video2podcast/functional/PipelineAssertionSteps.java:1033-1038 (`safe()`), and SummaryFlowIT.java:3032 (`check.safeText("private /tmp/secret")`) - the step "no Telegram message contains raw stderr, server diagnostic bodies or job filesystem paths" never checks for raw stderr. It looks for `w.root`, "private /tmp/secret" and "server diagnostic". "private /tmp/secret" is the body of the rejected-summary Telegram mock, not any process stderr. The stderr the fixtures actually emit is "download failed /tmp/secret" (the default `w.stderr`, used for the download, WAV and split failures), "PRIVATE content" and "Unsupported URL". None of these is checked. A leak of raw yt-dlp or ffmpeg stderr as an extra message would pass R8's "never send raw stderr" check. The SummaryFlowIT failed-download test, which sets stderr "download failed /tmp/secret", asserts a string that can never appear, so that assertion is vacuous. Fix: have `safe()` also reject `w.stderr` and "/tmp/secret", and have SummaryFlowIT assert on the stderr it injected. Checking edits as well as sends would be better still.
- [Suggestion] PipelineAssertionSteps.java:953-956 (`expiry`) and :1168-1173 (`eachOwner`) - both loop over `files` or `jobFiles()` with no size check. If `files` came back empty or no job.json were found, the assertions pass vacuously. The retention scenarios (delayed publication, PT30M) use `expiry` as their only assertion. Add `hasSize(2)` on the file entries and the job files.
- [Suggestion] PipelineWorld.java:2705-2706 and PipelineAssertionSteps `created()` - the clock is a `MutableClock` frozen at 10:00Z in every scenario except the delayed-publication one. "createdAt no later than summary publication" and "expiresAt = send time + 1h" therefore hold trivially there. Only the delayed scenario distinguishes publication-time retention from creation-time retention, and it does. This is acceptable, but a comment or a small clock tick in the main save scenario would make `created()` meaningful.
- [Suggestion] PipelineWorld.java:2509-2525 (`close()`) - `acceptedStatuses` is not reset when `completedFixture` clears `events` and `submissions`. In "Continue after a failed job" the wait for Done/Failed edits can never reach the count. It runs into the 10 s timeout on every run and only slows the suite. Reset the counter in `completedFixture` as well.
- [Suggestion] PipelineWorld.java:2297-2329 (`dirs()` / `job()`) - the "newest job" is chosen by directory creationTime. On filesystems without birth time this falls back to mtime, and ties at coarse granularity are possible. The scenarios are sequential, so this is unlikely to break, but it can flake. Consider tracking job directories by the first-seen order already kept in `seenJobs`.
- [Suggestion] MediaFixtures.java:525-567 - a missing fixture is generated into the source tree (`src/it/resources/media`) during the test run. The fixtures are committed, so this is a fallback only, but a test that writes into `src` can dirty the working tree.
- [Suggestion] Several step definitions ignore their parameters (`noWhisper(path)`, `wav(s)`, `chunks(a, b, c)`, `rejectSummary(body)`, `endpoints(a, b)`). They are harmless today but would not catch a different value in a scenario edit.
