# TD4 requirements: external-boundary scenario rewrite

Technical rewrite of the existing T8, T9 and TD2 scenarios, based on `SPEC.md`,
`tasks/todo.md`, `tasks/TD4/brief.md`, the analyst role and `whoami.feature`.
The combined MP4 success scenario specifies the already approved TD5 fallback;
TD4 changes specifications only. Original requirement tags remain scoped to
T8, T9 or TD2 by the feature tag; the R numbers below describe this rewrite.

## R1 — Only external stimuli and observations

Acceptance: every automated scenario starts work by sending a Telegram message
in a private chat, using the wording of `whoami.feature`. Preconditions configure
external mocks or fixtures; observations check Telegram calls, Whisper HTTP
requests, recorded process invocations or files. No step invokes a component,
reads an internal return value, or inspects a callback, thread or exception.

## R2 — Preserve the old coverage inventory

Acceptance: the tables below have one row for every original scenario, including
scenario outlines. Rewritten outlines retain their cases. Folded cases name the
destination. Removed cases identify existing unit tests. Ancillary internal
assertions moved out of retained scenarios are identified in the notes. No test
implementation is changed. Unit references are Java class and method names in
`src/test/java/com/video2podcast/` (media, transcript, job or config packages).

## R3 — Keep observable queue behavior

Acceptance: the queued stage edits the job's status message to
`Queued: position N`. N is the count of running and waiting jobs immediately
when this job is added (`JobQueue.size()`), including the newly added job.
The first job in an empty queue therefore shows position 1. A third job behind
one running and one waiting job shows position 3; after a job finishes
successfully or fails and the queue is empty, the next job shows position 1.
Feature assertions consistently say "the status text shows position N" and
check that outbound Telegram status edit, not a separate reply. This wording
and first-job behavior are the orchestrator's decision in
`A: TD4 architect review · orchestrator` and are now in T11 acceptance.
Future publication, callback ordering, throwable wrapping, serialization and
shutdown stay in `JobQueueTest`.

## R4 — Real media tools on success; defer harness wiring

Acceptance: every media success path uses real `yt-dlp` and `ffmpeg`. This
includes all T9 media preparation and both TD2 queue outcomes. Whisper, Ollama
and Telegram remain WireMock boundaries. Process mocks are permitted only for
failure injection and tool-argument checks. A successful mocked process response
may support such a check or reach a later injected failure, but cannot establish
a successful download, conversion, split or transcription flow.

Real audio property checks retain `@manual_media`, including 59/45/600-second
cases and the 1250-second remainder. The two new download scenarios are automated
specifications for T11, including real WAV/chunk property and source hash checks.
Mock argument scenarios assert only arguments, fixture bytes and request order;
they never claim their fake bytes prove conversion. Successful stderr warning
classification stays in `YtDlpClientTest#warningsOnStderrDoNotFailAnExitZeroRun`.

`src/it`, `CucumberIT` and its filters are untouched by TD4. T11 supplies fixture
assets, the decorator and step definitions, and removes all three exclusions
(`not @T8`, `not @T9`, `not @TD2`). Manual scenarios stay manual. TD4 does not make
these specifications executable today. The revision in the TD4 brief and backlog
takes precedence over the older fake-process defaults in SPEC/T11; the
orchestrator owns updating those documents, not this analyst revision.

## R5 — Local fixtures and no external DNS

Acceptance: small, deterministic audio/video fixtures are generated by `ffmpeg`
and kept in `src/it/resources`. WireMock holds those bytes and serves controlled
media pages and media responses with the correct `Content-Type` (including
`audio/mp4` for m4a, `video/mp4` for combined mp4 and the appropriate WebM type).
Pages expose the title, duration and available formats needed by real yt-dlp;
metadata is extracted by the real tool rather than fabricated by a process mock.
Fixture metadata and the recording's measured duration agree, especially at the
7200/10800-second inclusive limits. Low-bitrate generated recordings keep even
long-duration boundary fixtures small.

The harness's `ProcessRunner` is a thin decorator over the real runner: it adds
`--proxy http://127.0.0.1:<wiremock port>` to every yt-dlp invocation (metadata
and download), before the `--` URL separator, and delegates execution. It does
not fake output, rewrite URLs or create downloaded/WAV/chunk files. ffmpeg
invocations pass through to the real tool unchanged. This class name belongs to
the harness contract here, never to a Gherkin step.

`http://videos.example/...` is deliberately a made-up public host. yt-dlp uses
the loopback HTTP proxy to reach WireMock without resolving that host. Pages,
media URLs and any redirects stay on controlled HTTP fixtures; none contact
YouTube, a public DNS resolver or any other external host. WireMock supplies
all referenced assets and records the actual media requests. Literal URLs in
argument-check scenarios, including `unresolvable.example`, are handled only
by process mocks. DNS-free URL validation itself remains in unit tests.

## R6 — Separate audio and combined video downloads

Acceptance: “Download a separate m4a audio track and prepare WAV chunks” uses a
page offering a separate m4a audio track. Real yt-dlp produces exactly one
completed source, `source.m4a`, identical to the served fixture; real ffmpeg
produces 16 kHz mono signed 16-bit little-endian PCM WAV and a full-length chunk,
whose bytes reach Whisper.

“Download combined mp4 video with sound using the best fallback” offers only a
combined MP4 with audio and video, with no audio-only format. It checks the same
real preparation and Whisper upload with `source.mp4`. It is tagged `@TD5` and
specifies behavior after TD5 extends the selector to
`bestaudio[ext=m4a]/bestaudio/best`; it does not require TD4 to implement that
production change. The argument-only format preference scenario is also tagged
`@TD5` and records the post-TD5 selector, preserving m4a/audio-only preference
before the combined-format fallback. It uses process mocks only to check arguments.

## Boundary and fixture conventions

- A Telegram message is an update delivered through the normal bot boundary with
  the whole application wired. Replies/status edits are outbound Bot API calls.
  No step substitutes a direct media or transcription call.
- The real-tool/proxy Background is the default. A scenario's media-fixture step
  replaces the default recording at that URL before its Telegram message. This
  is an HTTP fixture, never a pre-populated job directory. The job's source,
  WAV and chunks must be created by the real download/conversion/split commands.
- T9 recordings of 59, 650, 1250, 1850 and 10800 seconds produce respectively
  1, 2, 3, 4 and 18 real chunks. Whisper responses are configured by filename and
  attempt. This preserves every original chunk-count and retry case without
  mocking media creation. Capture file bytes/hashes while each HTTP request is
  held or read; do not depend on temporary audio after successful transcription.
- A process-mock precondition explicitly overrides the real runner for that
  failure or argument scenario. Mock metadata, download, WAV and split responses
  are independently configurable, with successful defaults only to reach the
  specified check/failure. Such scenarios never resolve their literal URLs.
- In both T9 outlines with answer-timeout rows, `WHISPER_TIMEOUT=PT1S`;
  dedicated timeout scenarios retain their overrides. Held responses remain
  within the configured timeout. Post-transcription file checks run while
  Ollama's first answer is held, before summarization failure/cleanup can remove
  the job directory. Pending-Whisper file checks run after that request arrives.
  T8 source/audio assertions likewise run after Whisper receives the first chunk
  and while its answer is held; the source hash equals the served fixture hash.
- Failure assertions check safe Telegram messages, never enums or internal
  exceptions. They do not require failed-job audio to survive: the pipeline
  removes failed directories. Transcript preservation/atomic replacement stays
  in `TranscriptionClientTest#noSpeechLeavesAnExistingTranscriptUntouched` and
  `TranscriptionClientTest#aChunkFailureLeavesAnExistingTranscriptUntouched`.
  Absence of a transcript after terminal failure would be a vacuous assertion.
- Progress checks observe status-message edits. Retry count/order is observable
  at Whisper; backoff scheduling, supplied-list order, arbitrary input paths,
  transcript replacement and filesystem enumeration remain unit-level.
- In TD2 configure the first job's held or failed Whisper response before its
  link is sent. Wait for the first Whisper request before adding the other jobs
  when asserting position 3; wait for the first job's terminal Telegram outcome
  before sending the next link when asserting position 1.

## Out of scope

Unapproved product changes, production code (including TD5 implementation),
unit tests, fixture generation/storage, step definitions, integration tests,
runner/filter changes, T11 implementation, T18 deferred retry, delivery buttons
and commits. No external research was necessary; local approved sources and
existing tests supply the contract (reviewed 2026-11-17).

## Validation and handoff

The original mapping retains all 85 rows: 43 T8, 32 T9 and 10 TD2. The revised
files contain 46 scenarios/outlines. Static checks cover mapping destinations,
unit-test references, requirement/manual tags, example-table shape, external
message triggers, real-tool defaults and the `@TD5` combined-download tag.
No `./mvnw` command is run for this revision. The earlier verification in
`comms/questions.md` predates this revision and does not verify its new scenarios.
Architect and orchestrator must review the revised features and mapping; earlier
approvals apply to the earlier draft. T11 owns the future executable harness and
fixtures; TD5 owns the combined-format fallback.
